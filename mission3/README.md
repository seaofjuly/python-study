# Mini NPU Simulator

MAC(Multiply-Accumulate) 연산으로 입력 패턴이 **Cross(십자가)** 인지 **X** 인지 판정하는 Python 콘솔 프로그램입니다.
3×3부터 25×25까지 여러 크기의 패턴을 판정하고, 크기에 따라 연산 시간이 어떻게 늘어나는지 측정합니다.

## 1. 실행 방법

- Python 3.8 이상, 외부 라이브러리 없음 (표준 라이브러리 `json`, `time`, `re`, `os`, `sys`만 사용)
- `mission3` 폴더에서 실행합니다.

```powershell
py main.py
```

실행하면 모드를 고릅니다.

| 선택 | 모드 | 하는 일 |
|---|---|---|
| `1` | 사용자 입력 (3×3) | 필터 A, B와 패턴을 한 줄씩(공백 구분) 입력 → MAC 점수, 연산 시간, 판정(A/B/판정 불가) 출력 |
| `2` | data.json 분석 | `main.py`와 같은 폴더의 `data.json`을 읽어 일괄 판정 → PASS/FAIL, 성능 표, 결과 요약 출력 |

다른 JSON 파일을 분석하려면 파일 이름을 뒤에 붙입니다. (모드 2에서 사용)

```powershell
py main.py sample_error_data.json
```

## 3. 구현 요약

### 데이터 구조

- 패턴과 필터는 파이썬 2차원 리스트(`list[list[float]]`)로 저장합니다.
- `make_matrix(n)`, `get_value()`, `set_value()`로 n×n 배열을 만들고 특정 위치의 값을 읽고 씁니다.
- `check_matrix(matrix, n)`이 "n×n인지, 모든 값이 숫자인지"를 검사하고, 문제가 있으면 사유를 돌려줍니다.

### 라벨 정규화

data.json에는 같은 뜻의 라벨이 여러 모양으로 들어 있습니다. (`expected`는 `+`/`x`, 필터 키는 `cross`/`x`)
프로그램 안에서는 **표준 라벨 `Cross`, `X` 두 가지만** 쓰도록 `normalize_label()`에서 바꿔 줍니다.

| 원래 값 | 표준 라벨 |
|---|---|
| `+`, `cross` | `Cross` |
| `x` | `X` |

앞뒤 공백 제거와 소문자 변환을 먼저 하기 때문에 `Cross`, ` X ` 같은 값도 같은 라벨로 처리됩니다.
표에 없는 라벨은 `None`이 되고, 그 케이스는 FAIL로 처리됩니다. 판정 결과와 expected를 **같은 이름으로 맞춰 놓아야** `"+" == "Cross"` 같은 비교 때문에 잘못 FAIL이 나는 일이 없습니다.

### MAC 연산

```python
def mac(pattern, filt):
    total = 0.0
    for i in range(n):
        for j in range(n):
            total += pattern[i][j] * filt[i][j]
    return total
```

이중 반복문으로 같은 위치끼리 곱하고(Multiply) 더합니다(Accumulate). NumPy 같은 라이브러리는 쓰지 않았습니다.

### 동점 처리 정책 (epsilon)

```python
if abs(score_a - score_b) < 1e-9:
    return "UNDECIDED"
```

실수 계산에는 아주 작은 오차가 생기기 때문에 `==`로 비교하지 않고, 차이가 `1e-9`보다 작으면 동점(판정 불가)으로 봅니다.

### 모드 2 검증 순서

패턴 하나마다 아래 순서로 검사하고, 문제가 생기면 **그 케이스만 FAIL** 처리한 뒤 다음 케이스로 넘어갑니다. 프로그램은 멈추지 않습니다.

1. 키가 `size_{N}_{idx}` 형식인가? → N 추출
2. `input`, `expected`가 모두 있는가?
3. `expected`를 표준 라벨로 바꿀 수 있는가?
4. `size_N` 필터(Cross, X)가 있는가?
5. 패턴이 N×N이고 모든 값이 숫자인가?
6. MAC 점수 계산 → 판정 → expected와 비교

`sample_error_data.json`으로 실행하면 아래 오류들이 각각 FAIL로 처리되는 걸 확인할 수 있습니다.

```text
- size_5_4: 알 수 없는 expected 라벨 'cross??'
- size_5_5: 패턴 숫자가 아닌 값 포함 ('a')
- size_5_6: 스키마 오류 (input 또는 expected 누락)
- size_7_1: size_7 필터가 없음
- size_13_3: 패턴 크기 불일치 (입력 13×12, 기대 13×13)
- pattern_abc: 키 형식 오류 (size_N_idx 형태가 아님)
```

### 입력 검증 (모드 1)

- 한 줄에 숫자가 3개가 아니거나 숫자로 바꿀 수 없으면 `입력 형식 오류: 각 줄에 3개의 숫자를 공백으로 구분해 입력하세요.`를 출력하고 그 행렬을 처음부터 다시 입력받습니다.
- 모드 선택에서 1, 2 이외의 값을 넣으면 다시 묻습니다.
- `Ctrl+C`나 입력 종료(EOF)가 와도 안내 문구를 출력하고 조용히 끝납니다.

### 성능 측정

- `time.perf_counter()`로 **MAC 함수 호출 구간만** 측정합니다. (입력, 출력, 파일 읽기 제외)
- 크기마다 10회 반복한 평균(ms)을 출력합니다. 측정 전에 한 번 미리 실행(워밍업)해서 첫 호출 비용이 섞이지 않게 했습니다.
- 성능 표용 패턴은 패턴 생성기(`generate_cross`, `generate_x`)로 만들어서, data.json에 없는 3×3도 같은 방식으로 측정합니다.

## 4. 보너스 과제

- **패턴 생성기**: `generate_cross(n)`은 가운데 행·열, `generate_x(n)`은 두 대각선을 1로 채운 n×n 패턴을 만듭니다. 성능 분석에서 3/5/13/25 크기 입력을 만들 때 씁니다.
- **1차원 배열 최적화**: `flatten()`으로 2차원 배열을 길이 N²의 1차원 리스트로 펼치고, `mac_flat()`에서 인덱스 하나(`k`)로 접근합니다. 성능 표 아래에 같은 입력·같은 반복 횟수로 2D와 1D를 비교한 표가 나옵니다.

### 실패 원인 분석

실패한 3개(`size_5_1`, `size_13_2`, `size_25_1`)는 원인을 **데이터/스키마 문제 → 로직 문제 → 수치 비교 문제** 순서로 하나씩 확인했습니다.

1. **데이터/스키마 문제가 아닙니다.** 세 케이스 모두 키 형식(`size_N_idx`), 크기(N×N), `input`/`expected` 존재 여부 검사를 통과했습니다. 라벨도 `x`, `+`가 정규화되어 `X`, `Cross`로 정상 비교되었습니다. 만약 정규화를 하지 않았다면 판정 `X`와 expected `x`가 달라서 **6개 모두 FAIL**이 났을 것입니다.
2. **MAC 로직 문제도 아닙니다.** 손으로 계산한 값과 프로그램 점수가 같습니다.
   - `size_5_1` (X 입력): Cross 필터는 가운데 한 칸만 겹쳐서 0.9, X 필터는 대각선 9칸 × 0.1 = 0.9
   - `size_13_2` (Cross 입력): Cross 필터는 25칸 × 0.3 = 7.5, X 필터는 가운데 한 칸 = 7.5
   - `size_25_1` (X 입력): Cross 필터는 가운데 한 칸 = 4.9, X 필터는 대각선 49칸 × 0.1 = 4.9
3. **원인은 "수치 비교 문제"입니다.** 이 필터들은 일부러 두 점수가 수학적으로 **정확히 같아지도록** 가중치가 설계되어 있습니다. 그런데 컴퓨터는 0.1, 0.3 같은 수를 2진수로 정확히 저장하지 못해서, 여러 번 더하면 `0.8999999999999999`, `7.499999999999997`처럼 아주 작은 오차가 생깁니다.
4. 만약 epsilon 없이 `>`로만 비교했다면, 이 작은 오차 때문에 `size_5_1`은 Cross, `size_13_2`는 X, `size_25_1`은 Cross로 판정됐을 것입니다. 세 개 모두 expected와 반대라서 결과는 똑같이 FAIL이지만, **"오차가 우연히 어느 쪽으로 났는가"로 판정이 정해지는** 잘못된 결과입니다.
5. epsilon(`1e-9`) 정책을 적용하면 두 점수 차이가 `1e-15` 이하(예: 0.9 - 0.8999999999999999 ≈ 1.1e-16)라서 동점으로 보고 `UNDECIDED`를 냅니다. 미션 규칙상 판정이 expected와 다르면 FAIL이므로 `동점 규칙`에 의한 FAIL로 기록했습니다.
6. 즉 이 3개 FAIL은 **프로그램 버그가 아니라, 필터만으로는 두 모양을 구분할 수 없는 케이스를 정직하게 "판정 불가"라고 알려준 결과**입니다. 이 케이스들을 통과시키려면 비교 정책이 아니라 필터 가중치(데이터)를 고쳐서 두 점수 사이에 실제 차이가 생기게 해야 합니다.

### 성능 표와 시간 복잡도 분석

실행 예시 (컴퓨터마다 값은 다를 수 있습니다):

```text
크기       평균 시간(ms)   연산 횟수
------------------------------------
3×3             0.0008         9
5×5             0.0014        25
13×13           0.0067       169
25×25           0.0226       625

[보너스] 2차원 vs 1차원 배열 비교 (동일 입력, 10회 평균)
크기          2D(ms)    1D(ms)   1D/2D
------------------------------------
3×3         0.0008    0.0005    0.63
5×5         0.0014    0.0008    0.58
13×13       0.0065    0.0045    0.70
25×25       0.0226    0.0185    0.82
```

1. N×N 패턴의 MAC 연산은 모든 칸을 한 번씩 곱하고 더하므로 곱셈이 정확히 **N²번** 일어납니다. 그래서 시간 복잡도는 **O(N²)** 입니다.
2. 연산 횟수는 3×3에서 25×25로 갈 때 9 → 625, 약 **69배** 늘어납니다.
3. 측정 시간은 같은 구간에서 0.0008 → 0.0226 ms, 약 **28배** 늘어났습니다.
4. 69배보다 작게 늘어난 이유는, 크기가 작을 때는 함수 호출이나 반복문 준비 같은 **고정 비용**이 전체 시간에서 차지하는 비중이 크기 때문입니다.
5. 크기가 커질수록 고정 비용 비중이 줄어서 연산 횟수와 시간이 거의 비례하게 됩니다. 13×13 → 25×25는 연산 횟수 약 3.7배(169 → 625), 시간 약 3.4배(0.0067 → 0.0226)로 거의 같습니다.
6. 따라서 N이 2배가 되면 시간은 약 4배가 됩니다. 실제 AI 모델처럼 필터가 수백×수백이고 수천 개라면 연산량이 매우 빠르게 커지기 때문에, 많은 MAC을 동시에 처리하는 NPU 같은 병렬 하드웨어가 필요합니다.
7. 보너스로 만든 1차원 버전은 2차원 버전의 약 60~80% 시간으로 더 빨랐습니다. `pattern[i][j]`는 행을 한 번 꺼내고 그 안에서 다시 꺼내는 두 단계 접근이지만, `pattern_flat[k]`는 한 단계라서 접근 비용이 줄어듭니다. 다만 곱셈 횟수 자체는 똑같이 N²이므로 **시간 복잡도는 여전히 O(N²)** 이고, 줄어드는 것은 상수 부분뿐입니다.
